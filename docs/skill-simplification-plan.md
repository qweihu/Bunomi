### 已锁定的实现假设

- CLI 直接文本、位置参数或 stdin 输入时，stdout 输出 Ruby 转换内容片段，不包裹
  Markdown；
- CLI 使用 `--file` 输入时，在源文件同目录生成带本地时间戳的新 `.html` 文件；
- Agent Skill 默认生成独立 HTML；Markdown 仅在用户明确要求时导出；
- 翻译目标由 Agent 根据用户明确要求、当前指令语言和对话语境决定，核心库不强制
  `zh-CN`；
- 清洗、注音、翻译和校验不写中间 TXT 或 Markdown 文件。

## 1. 对需求的理解

当前问题不是功能不足，而是三个层次混在了一起：

1. Skill 的触发规则、默认行为和用户输出契约；
2. Bunomi / Utayomi 的应用流程与文件处理；
3. `japanese-language-core` 的通用读音、翻译和校验能力。

结果是 Agent 需要理解引擎选择、多个脚本、多个输出格式、路径安全、临时文件和
备用模式，Skill 变成了复杂应用的操作手册。目标是让 Skill 回到“收到什么任务、
默认做什么、结果长什么样”的简洁协议；复杂且可复用的确定性能力由
`japanese-language-core` 提供。

这次改造不是分阶段交付的产品拆分，而是一次围绕同一份新契约的联动改造。内部仍会
按依赖顺序修改和验证，但不把用户体验拆成多个阶段。

## 2. 目标边界

| 项目 | 面向用户的唯一主任务 | 不负责 |
| --- | --- | --- |
| **Bunomi** | 对用户提供的普通日语文本进行注音、翻译和校验，默认生成 HTML | 不生成课程或学习材料，不处理歌词清洗、歌词专属排版或歌词抓取 |
| **Utayomi** | 对用户提供的歌词或歌词 HTML 进行清洗、注音、翻译和校验，默认生成 HTML 歌词页 | 不抓取歌词，不提供多套特殊布局，不生成 Anki 卡片 |
| **japanese-language-core** | 为任何调用方提供可复用的读音、Ruby 对齐、翻译契约、结构校验和其他通用语言处理能力 | 不决定调用哪个 Skill，不承载 Bunomi / Utayomi 的产品流程和默认 UI |

`japanese-language-core` 是独立的通用库，不能假设只服务于 Bunomi 和 Utayomi。两个
应用可以使用它，但不能把应用专属规则反向写成核心库的默认行为。

## 3. Skill 契约

### 3.1 Bunomi

触发条件：用户要求给普通日语文本加读音、振假名、平假名或翻译。这里的“普通文本”
是相对于歌词工作流而言，不代表 Bunomi 要负责生成完整的日语学习材料。

默认行为：

- 使用平假名；
- 自动选择可用的共享读音引擎；
- 自动翻译，目标语言跟随用户当前指令和对话语境；
- 自动检查原文保留、Ruby 完整性和注音覆盖；
- 默认生成独立 HTML；
- 不询问引擎、词典、内部脚本或中间格式；
- 不访问网络，不根据歌名或 URL 补抓内容。

用户明确说“不翻译”时才关闭翻译；用户明确要求罗马音时才切换罗马音。

### 3.2 Utayomi

触发条件：用户提供歌词、歌曲文本、歌名/歌手信息，或要求处理歌词 HTML。

默认行为：

- 只使用用户提供的文本；
- 在内存中清洗 HTML 和页面噪音；
- 保留歌词换行、重复句、括号和和声标记；
- 使用共享读音能力添加平假名；
- 自动翻译，目标语言跟随用户当前指令和对话语境；
- 自动校验逐行对应关系和注音覆盖；
- 默认生成独立 HTML 歌词页面；
- 不访问歌词网站，不要求用户选择引擎或文件路径。

用户明确说“不翻译”时才关闭翻译；用户明确要求罗马音时才切换罗马音。

### 3.3 用户可见的结果格式

用户面向的格式只保留两种：

- **HTML**：默认、完整、可直接打开的结果；
- **Markdown**：用户明确要求时导出。

罗马音是不影响文件格式的注音模式；JSON 只保留为开发者或程序集成接口，不放进
默认 Skill 的功能宣传和结束提示；TXT 不作为处理中间产物或用户结果格式。

生成 HTML 后，Agent 可以用一句简短提示告知用户可继续要求：

> 如果你需要 Markdown、罗马音版本，或不需要翻译，可以继续告诉我。

这类提示属于 Agent 界面交互，不写成复杂的参数清单。

## 4. CLI 与 Agent 的区别

### 4.1 Agent 模式

Agent 模式默认产出最终 HTML。处理过程中的清洗、注音、翻译和校验全部在内存中完成，
不生成清洗 TXT、注音 TXT 或中间 Markdown 文件。Markdown 只在用户明确要求时作为
最终附加导出。

Skill 不提供任意输出路径配置。结果直接生成在用户可编辑的当前工作区域，由 Agent
界面负责展示和交互；用户如果需要把结果移动到其他位置，由用户和 Agent 的普通文件
交互完成，不由 Skill 设计一套路径管理流程。

### 4.2 CLI 模式

CLI 是直接的文本转换工具，不应默认包装成 Markdown 文档：

- 用户通过参数、stdin 或管道输入文本时，CLI 直接向 stdout 输出转换后的内容；
- 不额外添加说明、摘要或 Markdown 外壳；
- 用户输入文件时，在原文件所在目录生成一个新的结果文件；
- 结果文件名包含本地时间戳，默认不覆盖原文件；
- 不要求用户手工指定输出路径，也不创建额外的临时目录；
- 用户明确要求 Markdown 时，才生成 Markdown 文件。

默认文件名建议为：

```text
原文件名.20260807-153012.html
```

时间戳格式和“纯文本输入时是否输出 HTML 文档还是 HTML 片段”在实现前做一次最终
确认；两者都不能重新引入多层路径参数。

CLI 不负责调用大模型翻译。自动翻译是 Agent Skill 的默认行为；CLI 只负责确定性的
文本处理，或接收调用方已经准备好的翻译内容。

## 5. 翻译语言策略

三项目不再把中文或英文写成固定的 Skill 默认目标语言。

目标语言选择顺序：

1. 用户明确指定的目标语言；
2. 用户当前指令的语言；
3. 当前对话的主要语言环境；
4. 无法判断时，向用户询问一次，而不是擅自固定成中文或英文。

例如，用户使用德语说明“请翻译这段日语歌词”，则默认生成德语翻译；用户使用英语
说明，则默认生成英语翻译。歌词原文是什么语言，不决定译文目标语言。

在 `japanese-language-core` 中：

- 翻译契约必须接受调用方传入的目标语言；
- 语言注册表可以继续保存各语言的翻译约定；
- 核心库不根据 Bunomi 或 Utayomi 的产品偏好强制 `zh-CN`；
- Agent 模式仍由调用 Agent 完成翻译，不新增核心库内置供应商。

## 6. 流程优化

最终流程应当是单一内存管线：

```text
用户输入
  → 识别任务范围
  → 清洗（仅 Utayomi，内存）
  → 共享核心注音（内存）
  → 按用户语境自动翻译（内存）
  → 统一校验
  → 默认 HTML
```

Utayomi 不再把以下步骤暴露给 Agent 逐个编排：

```text
prepare_lyrics.py → utayomi_core.py → save_markdown.py → build_html.py
```

这些脚本可以拆成内部函数或由一个统一入口调用，但用户流程中只保留一个
“歌词输入 → HTML 输出”的入口。Bunomi 也应保持“文本输入 → 注音/翻译 HTML”的单一
默认路径。

## 7. 需要移除或降级的功能

从 Bunomi / Utayomi 的 Skill 契约和默认文档中移除：

- Anki 卡片和歌词挖掘卡片；
- 特殊布局、多主题或多种卡片版式；
- 引擎选择、legacy 模式、词典审计等内部配置；
- 清洗 TXT、注音 TXT 和翻译 TXT 等中间文件；
- 固定中文或英文作为默认翻译语言；
- “生成日语学习材料”这一泛化目标。

`japanese-language-core` 中已有的通用导出或 Anki API 是否物理删除，不能仅因两个
应用不再使用就直接决定；应先确认这些能力是否仍对独立核心库用户有价值。本次应用
改造会先把它们从 Bunomi / Utayomi 的用户路径和 Skill 入口完全移除。

## 8. 一次性落地范围

本次改造作为一个联动变更整体完成，包含：

1. 重写 Bunomi、Utayomi 的 Skill 和独立 Prompt，只保留触发、默认行为、输出和边界；
2. 更新两个 Skill 的触发元数据，使普通文本与歌词任务清晰分流；
3. 调整 Bunomi CLI：stdin/直接文本直接输出，文件输入自动生成同目录带时间戳的新文件；
4. 调整 Utayomi：由统一入口在内存完成清洗、注音、翻译和 HTML 生成；
5. 将 HTML 设为两个应用的默认用户结果，Markdown 作为显式可选导出；
6. 将自动翻译改为跟随用户语言环境，并支持明确的“不翻译”指令；
7. 收紧 `japanese-language-core` 的公共翻译契约，使其不绑定某个应用的默认语言；
8. 移除 Anki、特殊布局和中间文件在两个应用中的入口、文档和默认测试路径；
9. 保留必要的底层兼容 API，但不再让 Agent 直接面对它们。

这里的“整体完成”指用户契约一次性统一；具体修改时仍会先改核心契约，再同步应用
调用方，最后验证三个项目，避免某个项目先使用新接口而其他项目仍停留在旧接口。

## 9. 本地测试案例

测试不仅验证代码能运行，还验证 Skill 是否真的变简单。以下测试先在本地保留，
**不执行 `git add`，不纳入提交，不把临时测试加入发布内容**。

### Bunomi

- 普通日语文本默认返回注音和翻译结果，目标语言随用户指令语言变化；
- 明确“不翻译”时只返回注音；
- 默认平假名，明确要求后才使用罗马音；
- stdin 或直接文本输入只向 stdout 输出转换内容，不生成 Markdown 摘要；
- 文件输入在同目录生成新结果文件，文件名包含时间戳且不覆盖源文件；
- 输入原文、换行、标点和非日语片段全部保留；
- 无法判断日语时返回清晰错误，不由模型猜读音；
- 不再触发“生成日语学习材料”这类超出范围的任务。

### Utayomi

- 纯歌词文本默认生成 HTML，包含注音和翻译；
- 混杂 HTML、菜单、广告和脚本的输入只保留歌词内容；
- 清洗、注音、翻译过程不产生 TXT 或中间 Markdown 文件；
- 默认 HTML 中保留换行、重复副歌、括号和和声标记；
- 用户用德语或英语提出任务时，翻译跟随该语言；明确目标语言时以明确要求为准；
- 明确“不翻译”时保留日文注音但不生成译文行；
- 默认平假名，明确要求后才切换罗马音；
- HTML 生成失败时返回单一可理解错误，不要求用户手动执行多个脚本；
- Markdown 导出是显式请求，不成为默认结果；
- 不存在 Anki、特殊布局或歌词抓取入口。

### japanese-language-core

- reading API 保持原文和换行；
- Ruby 对齐在送假名、复合词和多音字场景下保持稳定；
- translation contract 接受任意已注册目标语言，不把 `zh-CN` 作为应用强制默认；
- 翻译结构校验保持一行对应一行，并保留占位符、标题和空行；
- 核心库不访问网络、不内置供应商、不依赖 Bunomi 或 Utayomi 的产品流程；
- Bunomi 与 Utayomi 同时调用同一读音和校验契约时结果一致。

### 触发边界

- 普通日语文本 → Bunomi；
- 歌词或歌曲 HTML → Utayomi；
- 单独要求通用翻译 → 共享翻译 Skill；
- 要求修改读音、翻译契约或核心 API → japanese-language-core；
- 同时明确多个项目 → 按用户指向联动修改；
- 无法判断项目范围 → 先询问，不擅自跨项目修改。
